    8. Authenticatie en autorisatie

    Bij elk verzoek spelen twee afzonderlijke vragen:

    • Wie is de gebruiker? Dit is authenticatie: de gebruiker heeft zich geïdentificeerd met een gebruikersnaam en wachtwoord, en elk volgend verzoek moet bewijzen dat het van hem of haar afkomstig is;
    • Heeft hij of zij toestemming om deze pagina te openen? Dit is autorisatie: in de casus beheert alleen een gebruiker met de rol ADMIN de artsen en clients.

    Omdat de server stateless is (hoofdstuk 6), moet het bewijs van identiteit bij elk verzoek worden meegestuurd. Daarvoor wordt een JWT-token ([JSON Web Token]) gebruikt: na het inloggen genereert de server een token met de identiteit van de gebruiker en ondertekent dat met een geheime sleutel. Het token wordt in een cookie opgeslagen; de browser stuurt het bij elk verzoek terug; de server controleert de handtekening. De gebruiker kan zijn token lezen maar niet wijzigen: elke wijziging maakt de handtekening ongeldig.

    [NestJS] leunt hiervoor op twee bibliotheken: [passport] (en de strategie [passport-jwt]), die tokens controleert, en [@nestjs/jwt], die ze genereert.

    import { Injectable } from '@nestjs/common';
import * as bcrypt from 'bcryptjs';

export interface User {
  id: number;
  login: string;
  name: string;
  role: 'ADMIN' | 'USER';
  passwordHash: string; // NOOIT het wachtwoord zelf
}

// de gebruikers, in het geheugen (het volgende hoofdstuk zet ze in een database).
// Het wachtwoord van elk van hen is hun login; alleen de bcrypt-hash wordt bewaard
@Injectable()
export class UsersService {
  private readonly users: User[] = [
    { id: 1, login: 'admin', name: 'Administrator', role: 'ADMIN', passwordHash: bcrypt.hashSync('admin', 10) },
    { id: 2, login: 'marie', name: 'Marie Pélissier', role: 'USER', passwordHash: bcrypt.hashSync('marie', 10) },
  ];

  byLogin(login: string): User | undefined {
    return this.users.find((u) => u.login === login);
  }
}
    • Regel 9: we slaan een wachtwoord nooit op; we slaan alleen de hash ervan op, een vingerafdruk die met een eenrichtingsfunctie wordt berekend. We kunnen controleren of een wachtwoord bij een vingerafdruk past, maar we kunnen het wachtwoord niet uit de vingerafdruk terugvinden;
    • Regels 16–19: [bcrypt.hashSync(password, 10)] berekent de hash met het algoritme [bcrypt]. Het getal 10 is de „kostenfactor”: bcrypt is opzettelijk traag (2¹⁰ iteraties) om te ontmoedigen dat iemand miljoenen wachtwoorden probeert. Twee hashes van hetzelfde wachtwoord verschillen (er wordt een willekeurige „salt” toegevoegd): [bcrypt.compare] zorgt voor de controle.

    import { Injectable } from '@nestjs/common';
import { JwtService } from '@nestjs/jwt';
import * as bcrypt from 'bcryptjs';
import { User, UsersService } from './users.service';

// wat het token bevat: genoeg om de gebruiker te identificeren zonder de database te lezen
export interface TokenContent {
  sub: number; // "subject": de identifier van de gebruiker (JWT-conventie)
  login: string;
  name: string;
  role: string;
}

@Injectable()
export class AuthService {
  constructor(
    private readonly users: UsersService,
    private readonly jwt: JwtService,
  ) {}

  // de gebruiker als het paar login / wachtwoord juist is, anders null
  async check(login: string, password: string): Promise<User | null> {
    const u = this.users.byLogin(login);
    // bcrypt.compare hasht het getypte wachtwoord en vergelijkt de hashes
    return u && (await bcrypt.compare(password, u.passwordHash)) ? u : null;
  }

  // een ONDERTEKEND token: de browser kan het lezen, maar niet wijzigen
  createToken(u: User): string {
    const content: TokenContent = { sub: u.id, login: u.login, name: u.name, role: u.role };
    return this.jwt.sign(content);
  }
}
    • regels 7–12: de inhoud van het token. [sub] ([subject]) is de gebruikelijke naam voor de id van de gebruiker. We nemen alles op wat de pagina's nodig hebben (naam, rol), zodat we niet bij elk verzoek de database hoeven te raadplegen;
    • regels 22–26: controle van de gebruikersnaam en het wachtwoord;
    • regels 29–32: [JwtService.sign] genereert het ondertekende token. [JwtService] wordt in de applicatiemodule geconfigureerd (sleutel, levensduur).

    import { Injectable } from '@nestjs/common';
import { PassportStrategy } from '@nestjs/passport';
import { Request } from 'express';
import { ExtractJwt, Strategy } from 'passport-jwt';
import { TokenContent } from './auth.service';
import { JWT_COOKIE, JWT_SECRET } from './constants';

// de ingelogde gebruiker, zoals de controllers die zien (req.user)
export interface LoggedInUser {
  id: number;
  login: string;
  name: string;
  role: string;
}

// de Passport-strategie "jwt": waar het token te vinden is en hoe het wordt gecontroleerd
@Injectable()
export class JwtStrategy extends PassportStrategy(Strategy, 'jwt') {
  constructor() {
    super({
      // het token wordt uit de cookie gelezen (en niet uit de header Authorization)
      jwtFromRequest: ExtractJwt.fromExtractors([(req: Request) => req?.cookies?.[JWT_COOKIE] ?? null]),
      ignoreExpiration: false, // een verlopen token wordt geweigerd
      secretOrKey: JWT_SECRET, // om de handtekening te controleren
    });
  }

  // aangeroepen als het token geldig is; wat het retourneert wordt req.user
  validate(content: TokenContent): LoggedInUser {
    return { id: content.sub, login: content.login, name: content.name, role: content.role };
  }
}
    • regel 18: een [Passport]-strategie, genaamd [jwt], beschrijft hoe een verzoek wordt geauthenticeerd;
    • regel 22: waar het token te vinden is: in de cookie. (Een [JavaScript]-client zou het in plaats daarvan meesturen in de header [Authorization: Bearer ...]; zie [ExtractJwt.fromAuthHeaderAsBearerToken()]);
    • regels 23–24: een verlopen of onjuist ondertekend token wordt geweigerd;
    • regels 29–31: wordt aangeroepen wanneer het token geldig is. Het resultaat is [req.user]: de ingelogde gebruiker, die toegang heeft tot acties.

    import { Body, Controller, Get, Post, Render, Res } from '@nestjs/common';
import { Response } from 'express';
import { AuthService } from './auth.service';
import { JWT_COOKIE, JWT_DURATION } from './constants';

@Controller()
export class AuthController {
  constructor(private readonly auth: AuthService) {}

  @Get('login')
  @Render('login')
  form(): object {
    return {};
  }

  @Post('login')
  async logIn(@Body() body: { login?: string; password?: string }, @Res() res: Response): Promise<void> {
    const user = await this.auth.check(body.login ?? '', body.password ?? '');
    if (!user) {
      // bewust vage melding: we zeggen niet welke van de twee onjuist is
      res.render('login', { login: body.login, error: 'Incorrect login or password.' });
      return;
    }
    // het token wordt in een httpOnly-cookie geplaatst: de JavaScript van de pagina
    // kan het niet lezen, de browser stuurt het bij elk verzoek terug
    res.cookie(JWT_COOKIE, this.auth.createToken(user), {
      httpOnly: true,
      sameSite: 'lax',
      maxAge: JWT_DURATION * 1000,
    });
    res.redirect('/profile');
  }

  // uitloggen WIJZIGT de toestand: het is een POST, geen link
  @Post('logout')
  logOut(@Res() res: Response): void {
    res.clearCookie(JWT_COOKIE);
    res.redirect('/login');
  }
}
    • regels 17–32: het inloggen. Als het inloggen mislukt, wordt het formulier opnieuw getoond met een bewust vage melding: als we zouden melden dat „deze login niet bestaat”, zou dat een aanvaller helpen geldige logins te vinden;
    • regels 26–30: bij succes wordt het token opgeslagen in een [httpOnly]-cookie; de [JavaScript] van de pagina kan het niet lezen, wat het token beschermt als er een kwaadaardig script op de pagina wordt uitgevoerd. [sameSite: 'lax']: de cookie wordt niet meegestuurd bij POST-verzoeken die vanaf een andere site worden verzonden, wat beschermt tegen request forgery ([CSRF]);
    • Regels 35–39: uitloggen verwijdert de cookie. Dit is een POST: het wijzigt de status van de gebruiker (zie voorbeeld 21).

    import { ArgumentsHost, Catch, ExceptionFilter, HttpException, HttpStatus } from '@nestjs/common';
import { Response } from 'express';

@Catch(HttpException)
export class ErrorsFilter implements ExceptionFilter {
  catch(exception: HttpException, host: ArgumentsHost): void {
    const res = host.switchToHttp().getResponse<Response>();
    const status = exception.getStatus();
    // 401 (geen token, of ongeldig token): door naar de inlogpagina
    if (status === HttpStatus.UNAUTHORIZED) {
      res.redirect('/login');
      return;
    }
    res.status(status).render('error', { status, message: exception.message });
  }
}

    Regels 10–13: een 401-fout toont geen foutpagina; de gebruiker wordt doorverwezen naar de loginpagina.

    import { CanActivate, ExecutionContext, ForbiddenException, Injectable } from '@nestjs/common';
import { Reflector } from '@nestjs/core';
import { Request } from 'express';
import { LoggedInUser } from './jwt.strategy';
import { ROLES_KEY } from './roles.decorator';

@Injectable()
export class RolesGuard implements CanActivate {
  // Reflector: het NestJS-hulpmiddel om metadata terug te lezen
  constructor(private readonly reflector: Reflector) {}

  canActivate(context: ExecutionContext): boolean {
    // @Roles van de actie, bij ontstentenis daarvan die van de controller
    const required = this.reflector.getAllAndOverride<string[]>(ROLES_KEY, [context.getHandler(), context.getClass()]);
    if (!required || required.length === 0) {
      return true; // geen @Roles: geen beperking op rollen
    }
    // req.user is ingesteld door JwtAuthGuard, die VÓÓR deze guard wordt uitgevoerd
    const user = context.switchToHttp().getRequest<Request>().user as LoggedInUser;
    if (!required.includes(user.role)) {
      throw new ForbiddenException(`the ${user.role} role does not give access to this page`);
    }
    return true;
  }
}
    • regel 10: [Reflector] is de service van [NestJS] die de metadata leest;
    • regel 14: de rollen die de actie vereist, of anders de rollen die de controller ervan vereist. Hier komt de uitvoeringscontext van de guard om de hoek kijken (zie hoofdstuk 7);
    • regels 15–17: zonder [@Roles] is er geen beperking;
    • regel 19: [req.user] is geregistreerd door de guard [JwtAuthGuard], die vóór deze guard wordt uitgevoerd;
    • regels 20–22: een ontoereikende rol leidt tot een 403-fout (Forbidden).

    import { Injectable } from '@nestjs/common';
import { randomUUID } from 'crypto';
import * as svgCaptcha from 'svg-captcha';

export interface Captcha {
  id: string; // geplaatst in een verborgen veld van het formulier
  svg: string; // de afbeelding, ongewijzigd in de pagina ingevoegd
}

@Injectable()
export class CaptchaService {
  // id -> verwacht antwoord. Het antwoord verlaat NOOIT de server
  private readonly answers = new Map<string, string>();

  generate(): Captcha {
    // svg-captcha: een willekeurige tekst, getekend met vervormde tekens
    const { text, data } = svgCaptcha.create({ size: 5, noise: 3, color: true, ignoreChars: '0oO1iIlL' });
    const id = randomUUID();
    this.answers.set(id, text.toLowerCase());
    return { id, svg: data };
  }

  // is het antwoord het juiste? In alle gevallen wordt de captcha
  // verbruikt: een afbeelding wordt slechts één keer gebruikt
  check(id: unknown, input: unknown): boolean {
    if (typeof id !== 'string' || typeof input !== 'string') {
      return false;
    }
    const expected = this.answers.get(id);
    this.answers.delete(id);
    return expected !== undefined && expected === input.trim().toLowerCase();
  }
}
    • Regel 13: de verwachte antwoorden worden door de server bewaard onder een willekeurige identificatiecode. De pagina bevat alleen de afbeelding en de identificatiecode: het antwoord verlaat de server nooit;
    • regels 15–21: de bibliotheek [svg-captcha] genereert een willekeurige tekenreeks en geeft die weer als afbeelding (SVG), verhuld door lijnen. Tekens die gemakkelijk met elkaar verward worden (0 en O, 1 en l, enzovoort) zijn uitgesloten;
    • regels 25–32: de controle verbruikt de CAPTCHA: een afbeelding wordt maar één keer gebruikt; een bot kan een antwoord dat hij al heeft gevonden niet hergebruiken.

    import { Injectable } from '@nestjs/common';

const MAX_FAILURES = 3; // getolereerde mislukkingen...
const BLOCK_MS = 60 * 1000; // ... vóór een blokkade van een minuut

// beperkt het aantal inlogpogingen per IP-adres
@Injectable()
export class LimiterService {
  private readonly counters = new Map<string, { failures: number; blockedUntil: number }>();

  // 0 als het IP-adres zijn geluk mag beproeven, anders het aantal seconden dat moet worden gewacht
  blockedSeconds(ip: string): number {
    const c = this.counters.get(ip);
    const remaining = c ? c.blockedUntil - Date.now() : 0;
    return remaining > 0 ? Math.ceil(remaining / 1000) : 0;
  }

  failure(ip: string): void {
    const c = this.counters.get(ip) ?? { failures: 0, blockedUntil: 0 };
    c.failures++;
    if (c.failures >= MAX_FAILURES) {
      c.blockedUntil = Date.now() + BLOCK_MS;
      c.failures = 0;
    }
    this.counters.set(ip, c);
  }

  success(ip: string): void {
    this.counters.delete(ip);
  }
}
    • regels 3–4: drie mislukte pogingen blokkeren het IP-adres gedurende een minuut;
    • regels 12–16: de resterende blokkeertijd;
    • regels 18–26 en 28–30: een mislukte poging wordt geteld; een geslaagde poging zet de teller terug op nul.

    import { Body, Controller, Get, Ip, Post, Res } from '@nestjs/common';
import { Response } from 'express';
import { AuthService } from './auth.service';
import { CaptchaService } from './captcha.service';
import { JWT_COOKIE, JWT_DURATION } from './constants';
import { LimiterService } from './limiter.service';

interface LoginBody {
  login?: string;
  password?: string;
  captchaId?: string;
  captcha?: string;
}

@Controller()
export class AuthController {
  constructor(
    private readonly auth: AuthService,
    private readonly captchas: CaptchaService,
    private readonly limiter: LimiterService,
  ) {}

  @Get('login')
  form(@Res() res: Response): void {
    this.display(res, {});
  }

  @Post('login')
  async logIn(@Body() body: LoginBody, @Ip() ip: string, @Res() res: Response): Promise<void> {
    // 1. een geblokkeerd IP-adres wordt niet eens beluisterd
    const seconds = this.limiter.blockedSeconds(ip);
    if (seconds > 0) {
      this.display(res, { login: body.login, error: `Too many attempts: try again in ${seconds} s.` });
      return;
    }
    // 2. de captcha, dan 3. de login en het wachtwoord
    const captchaOk = this.captchas.check(body.captchaId, body.captcha);
    const user = captchaOk ? await this.auth.check(body.login ?? '', body.password ?? '') : null;
    if (!user) {
      this.limiter.failure(ip);
      const error = captchaOk ? 'Incorrect login or password.' : 'The copied characters are incorrect.';
      this.display(res, { login: body.login, error });
      return;
    }
    this.limiter.success(ip);
    res.cookie(JWT_COOKIE, this.auth.createToken(user), {
      httpOnly: true,
      sameSite: 'lax',
      maxAge: JWT_DURATION * 1000,
    });
    res.redirect('/profile');
  }

  @Post('logout')
  logOut(@Res() res: Response): void {
    res.clearCookie(JWT_COOKIE);
    res.redirect('/login');
  }

  // elke weergave van het formulier heeft een NIEUWE captcha
  private display(res: Response, model: object): void {
    res.render('login', { ...model, captcha: this.captchas.generate() });
  }
}
    • regel 29: [@Ip()] injecteert het IP-adres van de client;
    • regels 32–35: een geblokkeerd IP-adres wordt niet eens verwerkt;
    • regels 37–38: eerst wordt de CAPTCHA gecontroleerd; het wachtwoord (waarvoor een rekenintensieve bcrypt-berekening nodig is) wordt alleen gecontroleerd als de CAPTCHA juist is;
    • regels 39–44: een onjuiste CAPTCHA telt als een mislukte poging;
    • regels 61–63: telkens als het formulier wordt getoond, wordt een nieuwe CAPTCHA gegenereerd.
